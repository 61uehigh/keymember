# 1Password security design analysis

> Source: 1Password Security Design White Paper (public PDF, 61 pages). `p.N` in the text refers to the page number.
> 1Password is closed source and its terms restrict reverse engineering, so we relied **only on public documents** and did no binary analysis.
> The white paper does not cover Travel Mode, Watchtower (breach checks), or per-request MACs.

## 1. Core idea: Two-Secret Key Derivation (2SKD)

**Goal**: make offline brute force impossible even if the entire server DB leaks.

### Secret Key (p.5–6, p.21)

- Generated by the client at signup and stored only on devices. Users do not memorize it.
- Format: `A3-ASWWYB-798JRYLJVD4-23DC2-86TVM-H43EB`
  - The first part is the version (`A3`), next is the account ID (not secret), and the rest is 26 random characters.
- Alphabet: 31 characters, leaving out the easily confused 0/1/I/O/U. 31²⁶ ≈ 2¹²⁸·⁸, so it carries more than 128 bits of entropy.

### Key derivation (p.10, p.22–23)

```
password  ─ trim + NFKD ─┐
salt16 ─ HKDF(salt=lower(email)) ─► PBKDF2-HMAC-SHA256(650,000 iterations) ─► 32B ─┐
                                                                                  XOR ─► AUK  (for encryption, kid "mp")
SecretKey ─ HKDF(salt=AccountID, info=version) ─► 32B ─────────────────────────────┘

same pipeline + independent salt ─► SRP-x  (for authentication)
```

- The password is trimmed of leading and trailing whitespace and Unicode NFKD-normalized.
- The salt is bound to the lowercased email, so only the user can change their email, and this constraint is enforced cryptographically (p.32).
- AUK (encryption key) and SRP-x (authentication key) are **derived separately with different salts**.
  - SRP-x is encrypted with the AUK and cached locally, so a normal unlock runs the KDF only once.
- PBKDF2 was chosen because it is the only KDF WebCrypto supports. They say they wanted Argon2 but gave it up because of browser constraints (p.23, p.48).

**Effect**: even with full control of the server, an attacker gets only AUK-encrypted private keys and SRP verifiers. Without the Secret Key, every password guess fails the same way, right or wrong (p.9, p.53).

**Limit**: the Secret Key only protects against a server breach. **If a device is compromised**, password strength is the only defense left (p.51).

## 2. SRP authentication (p.7–9, p.53–55)

- SRP-6 with a swapped-in KDF. The groups are RFC 3526 MODP (2048 bits or more).
- The server never receives the password. It receives only the verifier `v = g^x`, once, at signup.
- The server must also prove it holds `v`, giving **mutual authentication independent of TLS**.
- Every request is additionally encrypted with AES-GCM under the session key K, so transport is protected three ways: E2EE at rest, TLS, and SRP session encryption (p.43).
- **Admitted limit**: messages are encrypted individually, so replay attacks are not prevented (p.43).

## 3. Key hierarchy (p.10–12, p.25)

```
AUK ─► personal keyset symmetric key ─► RSA-OAEP-2048 private key ─► vault key (AES-256) ─► items
                                                                    └─ also wrapped with the Recovery Group public key
```

- A **keyset** is in JWK format and carries an `encryptedBy` field and an algorithm ID.
  - Algorithm changes follow this order: ship support for reading the new format → generate in the new format → re-encrypt → the server rejects uploads in the old format.
- An **item** is split into two parts, each encrypted separately with AES-256-GCM.
  - `overview`: title, URL, tags. Used for listing, search and URL matching.
  - `details`: passwords, notes.
  - So showing a list does not require decrypting everything.
- **Files** are each encrypted with their own key, which is wrapped with the vault key (p.31).
- **Left in plaintext on the server** (p.46): user names and emails, group names, device info (IP, OS), public keys, MFA secrets, invitation details.
  - Item contents (including the overview) and keys are all encrypted.

## 4. Sharing, groups and recovery

- **Sharing** (p.13): the vault key is wrapped with the recipient's public key. The server never sees the plaintext vault key, so **the server cannot create a share on its own.**
- **Groups** (p.34): groups have keysets too. Membership means the group's private key is wrapped with the member's public key.
- **Recovery Group** (p.34–36): every vault key is also wrapped with the Recovery Group public key. Recovery works like this:
  1. An admin starts recovery, which suspends the user's account.
  2. If the user signs in with their existing credentials, recovery is cancelled automatically.
  3. The user creates a new Secret Key and a new keyset through a signup-like flow.
  4. Only then does the server hand the wrapped vault keys to the admin.
  5. The admin rewraps the vault keys with the user's new public key.

  At no point can the admin see the user's password or vault data.
- **Recovery key** (p.36–37): HKDF derives authentication, encryption and UUID subkeys from a 32-byte random value.
  - Server policy: reject if the user signed in within the last hour, and reject if there was an aborted attempt within 24 hours.
- **Share links** (p.14–20): the secret goes in the URL fragment (`#...`) so it is never sent to the server.
  - HKDF derives the key, UUID and token separately from the same secret. **Knowing the UUID alone does not authenticate.**
  - Expiry, view-count limits and email verification can be applied.

## 5. Devices, SSO and passkeys (p.24–30)

- **Emergency Kit**: a printable PDF with the Secret Key and a QR code. 1Password cannot reset passwords, because a reset feature would itself be an account takeover path.
- **SSO/passkey accounts**: instead of a password and Secret Key they use a **random AUK and SRP-x** (the credential bundle).
  - The bundle is encrypted with a per-device device key and stored on the server.
- **Linking a new device**: the existing and new devices run **CPace PAKE** over a 6-digit code and confirm the key with an HMAC, so tampering by the server in the middle is detected.

## 6. Three levels of access control (p.32–33)

| Level | What it enforces |
|---|---|
| Cryptography | Decryption, sharing, email changes |
| Server policy | Read-only enforcement, delivery of vault data, recovery approval |
| Client | Export, revealing passwords, printing. **Easily bypassed with developer tools** |

Openly documenting which control is enforced at which level is a strength in itself.

## 7. Developer features: Connect and Service Accounts (p.38–42)

- A service account is a special user with a random password. It cannot reshare vaults.
- Credentials are split in two: an encrypted file lives on the server, and the key to decrypt it lives inside the bearer token.
- JWTs allow **ES256 only**.

## 8. Admitted weaknesses ("Beware of the leopard", p.47–52)

| No. | Weakness | keymember's approach |
|---|---|---|
| A.1 | If TLS or hosting is compromised, the web client can be served malicious JS | Keep the web vault minimal and favor the extension and desktop apps |
| A.2 | The Recovery Group cryptographically holds every vault key | Minimize who has recovery rights and keep audit logs |
| A.3 | **No public key verification**, so a malicious server can substitute public keys | Introduce signed public keys and fingerprint verification |
| A.4 | Removing a member **does not rotate keys** | Offer vault key rotation on member removal |
| A.5 | Changing the password leaves the keyset unchanged | Offer keyset rotation on password change |
| A.10 | The Secret Key is powerless against device malware | Use the OS keychain and hardware keys |
| A.11 | Email registration can be discovered (enumeration) | Make prelogin responses uniform |

## What keymember takes from it

1. **2SKD**: combine a Secret Key with the password, used only within the defined threat model. See the [design document](../design/crypto.md) for details.
2. **Separate encryption of overview and details**, for URL matching and list performance.
3. **Group keyset-based sharing** and **admin recovery** (the Recovery Group approach).
4. **Fragment secrets and HKDF separation for share links.**
5. **Emergency Kit** and adding devices by QR code.
6. **Document the three levels of access control.**
7. Fixes for the weaknesses 1Password admits: Argon2id, public key signatures, key rotation, replay protection.
