# Security review record (October 2026)

This is the record of an internal review done ahead of the external security review. External reviewers should start with "Known remaining risks" and "Requests for the external review" in this document.

## Method

- **Code review**: Split into four areas (server routes, core and client cryptography, the browser extension, and web/SSO/share links) and reviewed with AI code review (Claude). No human security expert has reviewed it yet. Each finding was confirmed by re-tracing the code path before it was fixed.
- **Fuzzing**: Used fast-check to feed random and mutated input to every place that accepts untrusted input: CBOR, envelopes (random bytes, single-bit flips), key wrapping, signature verification, the 4 import parsers, PKCS#8, share links, TOTP, URL matching, the extension message validator (differential comparison of the hand-written validator against the zod schema), and OIDC ID tokens.
- **Mutation testing**: Removed or disabled key defensive code one piece at a time and checked that tests failed.
- **Real browser**: Ran autofill, OTP, save prompts, and passkey registration and login end to end in Playwright Chromium.

## What was fixed

Severity reflects the assessment at the time of the review.

| Severity | Issue | Fix |
|---|---|---|
| High | If the server wrapped an arbitrary vault key with a user's public key, the client used it as-is (new items were written under a key the server knew) | Vault key grants carry a granter signature (`keymember/key-grant/v1`). Sync accepts only grants signed by the user themselves or a certified member, and uses only group keys whose certificate has been verified |
| High | On certification, the role and email were signed using values supplied by the server (if the server made a member an admin, the copy of the recovery key went with it) | The admin signs the email and role when inviting, and certification takes the role from that signed invite |
| High | The extension's owner pinning didn't compare the displayed key with the pinned key | Pin only when it matches the fingerprint the user compared |
| High | On recovery completion, the user id supplied by the server was used as-is | Checked against the recovery request signed by the requesting admin |
| High | A single admin could create a second admin account and pass two-person approval alone | An admin certified by the requester within the last 7 days can't approve |
| Medium | The server received and checked the login secret (authKey) | Sign a one-time challenge with an Ed25519 login key (ADR-003 updated). Existing accounts switch over at their next login |
| Medium | A suspended member's pending recovery remained and could let them back in, and the recovery steps had a race condition | Suspension cancels recoveries and invites, UPDATEs are conditional on state, and the snapshot is taken at approval time |
| Medium | A personal vault could be shared via key rotation / the last admin could be demoted | The server rejects both |
| Medium | Two-factor authentication could be changed with only a token | Requires a code from the existing authenticator app |
| Medium | Phishing by sending an SSO link to a victim and getting them to confirm it | A confirmation page showing the device, time and a warning before going to the provider |
| Medium | Clickjacking of the inline menu and key button | Uses IntersectionObserver v2 to accept clicks only after the element has actually been visible for 500 ms, and closes the menu when it's obscured |
| Medium | Autofill also filled hidden third-party iframes | Fills only the top frame and frames with the same origin |
| Medium | Passkey UV meant "unlocked within the last 5 minutes" | UV only when the password was entered during this request. The consent window becomes active 500 ms after gaining focus, one per tab |
| Medium | Share link secrets stayed in the address bar and history | Removed from the URL after being read |
| Low | Others, including SSO ticket expiry, a subject race, revoking provider tokens on logout, requiring Google `hd`, HSTS, login rate-limit keys, a TOTP reuse race, forged save prompts, forced revocation of share links, passkeys on the sandbox origin, and reduced extension permissions | All addressed |

Found by fuzzing:

- The envelope's key id (`kid`) wasn't protected by the AEAD and wasn't compared against the opening key. It now has to match the opening key's id.
- A malformed ID token raised a `SyntaxError`, and the callback returned a 500. It's now rejected with an `OidcError`.

## Known remaining risks

- **Collusion between a certified member and the server**: Grant signatures only check whether a certified member signed the grant. Only the server knows whether that member has permission to manage that vault. If a certified member colludes with the server, they can hand a vault key they know to another member.
- **Rollback**: Devices can't detect the server re-serving an old group certificate or an old vault generation (there's no per-device record of the highest version seen). The server checks group key versions when sharing.
- **Certificate revocation and recovery key rotation**: There's no signed structure for revoking a departed admin's certificate, and the recovery key never changes once created. When an admin leaves, their copy of the recovery key remains.
- **List of vaults to recover**: Uses the snapshot the server stored. There's no screen yet that shows the completing admin the names of the vaults to be restored.
- **Account keyset rollback**: The AAD of the account key seal doesn't include the keyset version, so unless the password has been changed, the server can serve an old keyset again.
- **Admins opening group vaults**: Admins who aren't in a group can still open the group key using their copy of the recovery key (intended by design, crypto.md §5).
- **Extension**: A site can guess, without a window appearing, whether a passkey is registered (allowCredentials probing). A password waiting to be saved stays in the extension's session storage in plaintext for 60 seconds. Host permissions are broad (needed for autofill).
- **SSO phishing**: The confirmation page only reduces it; it can't fundamentally stop an attacker who has the password from tricking the victim into confirming (the CLI can't be bound to a browser).
- **Login method exposure**: During the transition period, prelogin reports accounts that haven't switched over yet as `legacy`.

## Requests for the external review

2. The real impact and priority of each item in "Known remaining risks" above
3. The browser extension's autofill and passkey paths (especially clickjacking and origin decisions)
4. Server permission checks (especially recovery, groups and share links)
